# Claude Code 与 Antigravity 网关长流断裂、重试风暴与会话中毒深度排查诊断报告

本报告系统性总结 Claude Code（以 v2.1.28x ~ v2.1.293 为代表）配合 Antigravity 网关在处理大计算/复杂长输出（典型如高细节 SVG、多文件大工程修改）时遭遇的各类错误症状、客户端逆向证据链、逐格原因排查与网关稳态治理策略。

---

## 一、错误症状全景总结 (Symptoms Catalog)

| 症状代号 | 客户端表象 | 触发场景 | 持续影响 |
| :--- | :--- | :--- | :--- |
| **S1: 重试风暴死循环** | 终端出现橙色警告并倒计时：<br>`Retrying 6/10 · 27m 24s` 或 `Retrying 8/10 · 16m+` | 长耗时生成任务（如 100s+ 无新 Token 输出或网络中间件掐断流） | 单次请求挂起近半小时，用户体验彻底瘫痪 |
| **S2: 会话永久中毒** | 当前轮次中断后，用户输入任何新内容，该会话均持续秒报 400 错误或再度静默超时无法恢复；但**新建空白对话却完全正常** | 上一次请求在中途发生断流（特别是思考块输出后正文未开始时断开） | 该本地会话无法继续使用，丢失上下文连续性 |
| **S3: 幽灵 429 与假限额** | 客户端突然弹出 `Quota Exceeded` 或 `429 Too Many Requests`，但实际上账号配额完全充裕 | 客户端历史版本硬编码或配置文件使用了过期虚拟模型 | 阻断用户调用，误导用户以为账号被风控 |
| **S4: 客户端主动掐线 (Client RST)** | 终端在无报错提示下突然截断停止输出，网关收到下游 Broken pipe | 客户端内部非流式超时定时器触发（`monotonicNow() - Cy >= uon()`） | 提前截断合法推理，产生半成品代码/文件 |

## 二、逐格原因深度排查与证据链分析

### 症状 S1: 客户端 27+ 分钟重试风暴死循环
#### 1. 现象与机制追踪
在之前的调试中，曾尝试将中途断流错误“如实向客户端透传底层 Err”，期望触发客户端原生的快速重试。然而这引发了严重的重试死锁：客户端不是重试一次，而是连续重试 10 次，退避间隔呈指数暴涨，累计高达 27~29 分钟。
#### 2. Claude Code 逆向源码证据链 (Decompiled from v2.1.293)
```javascript
function PU(e) {
  if (!(e instanceof xt)) return !1;
  return e.status === 529 || (e.message?.includes('"type":"overloaded_error"') ?? !1);
}
```
```javascript
// 流失败决策引擎:
let Ru = Qnn({
  error: Ia,
  isServerError: jm,
  stalled: kp,
  isConnectionError: Sd || pc,
  complete: qu !== null && zb && El === null // 核心不变式
});
let Mp = Ru === void 0 ? "keepPartial" : __.onStreamFailed(Ru, !Al);
```
- **关键根因 1 (错误类型踩坑)**：网关之前向客户端下发过合成的 `"type":"overloaded_error"`。`PU(e)` 只要检测到该字符串，无条件将错误原因归类为 `"overloaded"`。
- **关键根因 2 (重试算法阶梯)**：当归类为 `"overloaded"` 或流未完成断裂且存在思考块时，Claude Code 会强制进入阶梯退避重试（Backoff Schedule），第 1 次等待数秒，第 8~10 次单次等待时间达数分钟，累积达 27 分钟。
- **治理与结论**：
  - **绝不能**在流中途断裂时发送 `"overloaded_error"`。
  - 一旦正文或思考已经输出给客户端，网络异常**绝不能作为底层连接中断向外流出**，而必须由网关状态机在本地优雅闭合（发送 `end_turn` 与 `message_stop`），满足 `complete: true`，促使客户端执行 `"keepPartial"` 正常收尾，把重试决策权交还给用户。

### 症状 S2: “坏会话永远坏，新会话一开始好” (会话历史中毒)
#### 1. 现象与机制追踪
为什么出问题的旧会话怎么重试都不行，而开一个新会话就没问题？
#### 2. Claude Code 逆向源码证据链 (Decompiled from v2.1.293)
```javascript
if (Qe && E.type === "assistant" && !E.isApiErrorMessage) {
  E.resumedFromIncompleteThinking = !0;
}
```
- **关键根因**：当一个流在输出 `thought` 块后发生断裂、或者正文块未闭合（`El !== null`）时，Claude Code 会把该残缺的 Assistant 消息固化到本地 JSON/SQLite 历史记录中，并打上 `resumedFromIncompleteThinking = true` 的永久脏标记。
- **级联崩溃**：当用户在该会话中继续提问时，客户端打包历史上下文并重新向网关发送。此时该 Assistant 消息内部的思考块**没有合法的 Thought Signature，也没有标准闭合标签**。上游 Gemini 校验到畸形的历史上下文后，直接拒绝执行（报 400）或陷入计算死锁，导致该会话永久瘫痪。
- **治理与结论**：
  - 网关在捕获到中断时，若检测到 `has_thinking && !has_content`，**强制自动闭合思考块**（发送 `content_block_stop`），并注入兜底文本块，随后发出 `end_turn`。
  - 这保证了客户端存储的该轮 Assistant 消息是一个“合法、完整”的转折点，彻底阻断 `resumedFromIncompleteThinking` 脏状态。
  - **针对已中毒的旧会话**：必须在终端执行 `/undo` 撤回出错的那一轮，或执行 `/compact` 压缩上下文，才能恢复健康。

### 症状 S3: 幽灵模型与上游 429 假限额
#### 1. 现象与机制追踪
调用突然报 429，提示账户没有余额或频次超限。
#### 2. 根因排查
- 客户端或旧配置文件请求了例如 `claude-sonnet-4-6-thinking` 这种上游实际不存在的虚拟模型标识。
- 上游模型在收到未知模型路径时返回非标状态码，被网关或适配器误判为限额并触发连续轮换，最终导致账号池耗尽报错。
- **治理与结论**：
  - 网关全面推行 `OfficialModelCatalog`，所有官方模型动态派生，彻底清除内置硬编码。
  - 对非标幽灵模型建立拦截与平滑重定向机制（如映射回 `claude-sonnet-4-6`）。

### 症状 S4: Gemini 间歇性断连与客户端主动超时掐线
#### 1. 现象与机制追踪
用户观察到：“Gemini 经常断联，但一般几十秒内恢复；现在客户端似乎会强行断开连接”。
#### 2. 客户端机制与网关保活
- **客户端行为**：Claude Code 在无数据接收时维护了一个超时监测器（`outlastedNonStreamingTimeout: he.monotonicNow() - Cy >= uon()`）。若超过客户端容忍时间，客户端会单方面发送 TCP RST 关闭连接。
- **上游行为**：Google GFE / 中间件在复杂生成时有 100~116 秒的无数据断流断崖。
- **网关保活关键**：
  - 网关必须持续且高频地向下游客户端发送 SSE 保活心跳（`: keepalive\n\n`，每 3 秒一次），不断重置客户端的 `Cy` 计时器，防止客户端单方面主动掐线。
  - 同时网关对上游 Gemini 保持 120s+ 的平稳等待窗口，允许模型在 40~90s 内完成复杂坐标运算并恢复输出。

## 三、版本建议与规避指南 (Recommendations)

### 1. 建议使用的客户端版本
- **稳定推荐版本**：
  - **Claude Code v2.1.28x**（在此版本之前，流终结检查相对宽松，容错能力更强）。
- **最新版 v2.1.293+ 的适配要求**：
  - 如果使用 v2.1.293 或更高版本，**必须配合包含本 PR (#3634) 修复的 Antigravity 网关**。
  - 本 PR 严格满足了 2.1.293 的三元组契约 `qu !== null && zb && El === null`，可在最新客户端下彻底消除 27 分钟重试风暴。

### 2. 用户操作指南 (如果遇到中断)
- **切勿任由客户端倒计时重试**：如果看到重试倒计时，直接按 `Ctrl+C` 中断。
- **恢复损坏会话**：输入 `/undo` 撤销最后一次中断的消息，然后重新输入即可无损继续。

## 四、关于“9月版本回退”的反思与演进

- **9 月版本机制的核心精髓**：在于**“一旦已向客户端输出内容，中途遭遇断流必须平稳收尾（发送 `end_turn`），严禁抛出异常诱发死循环”**。这一原则在今天依然是防御客户端退避死锁的唯一可靠解。
- **9 月版本的局限性（已改进）**：旧版回退曾丢失了过渡断崖期（Thinking 结束到 Content 开始之间）的三阶段梯度超时，且缺乏对 Thinking-only 断流的文本兜底。
- **本次最终方案**：将 9 月稳态收尾逻辑作为底层基石，与现代的三阶段流生命周期（`stream_lifecycle.rs`）及 2.1.293 严格块闭合契约（`El === null`）深度融合，既保留了长流高防卡死能力，又完全消除了会话中毒副作用。
